# M12D TV 全量异常系统审计与重设计基线（2026-07-11）

## 1. 审计目的

本审计回答两个问题：

1. 为什么 205 当前发布的 377 个 TV SKU M12D 画像全部需要复核，且没有一个 `ready`。
2. 如何重设计输入质量、锚点评分、画像状态和发布门槛，使绝大多数有充分证据的 SKU 正常可用，同时保留真正证据不足的少数 SKU。

本轮只对 205 `catforge_dev` 执行 SELECT 和离线影子测算，没有修改生产表、M12D 生产逻辑、竞品排序逻辑或发布版本。

## 2. 结论

当前不是 377 个 SKU 各自存在严重数据问题，而是质量状态被逐层放大的系统问题：

1. 上游把范围说明、过滤说明、历史缺失标记和局部待复核项统一视为 `partial/conflict`。
2. M12D 使用通用 `_profile_status` 和最坏值 `_combine_statuses`，任意一条质量标记即可降级整个模块，任意一个模块降级即可给 SKU 的所有锚点统一扣分。
3. `missing_or_partial_inputs` 对每个锚点扣 1 分、降低 0.1 置信度，并再次降低画像置信度。
4. `review_required` 被用来表示“存在任何提示”，而不是“存在会改变业务结论的阻断问题”。
5. 竞品分析把这种系统性降级当成真实画像不可用，进一步改变候选角色和 Top 3。

最直接的反证是 M03B：377 个 SKU 均报 1 个参数冲突，经重建后 377 个冲突全部来自 `screen_size_segment`。原始值 `≥70` 与派生标准值 `xlarge_70_85`、原始值 `60-69` 与派生标准值 `large_60_69` 被按字符串不同判成冲突，实际是同一尺寸事实的两套编码，不是业务事实矛盾。

## 5. M12D 放大链路

当前通用状态函数包含以下行为：

```text
任意 quality_flag -> 模块 partial
任意 review_required -> 模块 partial
任意模块 partial/missing -> 组合状态 partial
任意输入 partial/missing -> 所有锚点增加 missing_or_partial_inputs
missing_or_partial_inputs -> 每个锚点 -1 分、-0.1 置信度
partial 输入数量 -> 画像置信度再次每项 -0.05，最多 -0.25
存在任意 partial -> review_required
```

这套算法混淆了四件不同的事：

- 数据有没有。
- 数据能不能用于当前锚点。
- 是否存在提示性限制。
- 是否存在会改变结论的阻断问题。

它还把行级、关系级、锚点级问题不加区分地传播到 SKU 画像级，因此会出现“所有 SKU 都异常”的结果。

## 6. 影子测算

影子测算没有放宽购买理由 taxonomy、场景门槛、弱表达封顶或真实负向风险，只做一项修正：删除由全局 `partial` 产生的 `missing_or_partial_inputs` 统一扣分，并重新按既有强证据阈值和场景门槛判断 `core_payment`。

结果：

| 指标 | 当前 | 影子测算 | 变化 |
| --- | ---: | ---: | ---: |
| 有核心成交理由的 SKU | 257 | 332 | +75 |
| 无核心成交理由的 SKU | 120 | 45 | -75 |
| 核心成交理由覆盖率 | 68.2% | 88.1% | +19.9pp |

剩余 45 个 SKU 的最佳影子证据分分布：

| 最佳分 | SKU 数 | 处理建议 |
| ---: | ---: | --- |
| 8 | 9 | 接近强证据门槛，按缺失证据域标为 `ready_limited`，不得自动抬升为核心理由 |
| 7 | 18 | 保留辅助成交理由，补评论、语义或支付价值证据后再升级 |
| 6 | 6 | 中等证据，保持辅助理由 |
| 5 | 12 | 弱表达或输入明显不足，不进入强竞品锚点比较 |

影子测算同时暴露另一个风险：取消全局扣分后，部分 SKU 会出现 5-7 个强锚点。重设计必须把生效的 `core_payment` 限制为最多 3 个，并按锚点族去重；不能用修复降级问题的方式制造核心理由泛滥。

## 7. 重设计原则

### 7.1 三轴质量模型

每个输入不再只有一个最坏值状态，而是分别记录：

| 轴 | 取值 | 含义 |
| --- | --- | --- |
| `availability` | `present/missing` | 当前 serving scope 是否有输入 |
| `usability` | `usable/limited/unusable` | 对当前锚点能否使用 |
| `issue_severity` | `info/warning/blocking` | 问题是否会改变当前锚点或画像结论 |

`info` 不扣分，`warning` 只作用于相关证据或锚点，`blocking` 才能阻断锚点或触发人工复核。

### 7.2 问题按作用域传播

每条问题必须声明 `scope`：`row/relation/anchor/profile/release`。传播规则为：

- 行级问题只影响引用该行的证据。
- 关系级问题只影响该任务、客群或战场关系。
- 锚点级问题只影响命中的购买理由。
- 只有无可用核心锚点、身份冲突、关键事实冲突或版本不一致，才能升级为画像级阻断。
- 只有系统性覆盖异常或质量门槛不达标，才能升级为发布级阻断。

### 7.3 当前 serving scope 优先

`*_missing` 等历史标记不得直接成为当前 M12D 的输入状态。M12D 必须根据本次选中的上游版本和 batch 重新判断依赖是否存在；历史标记仅保留为 lineage 记录。

### 7.4 锚点级评分

- 删除全 SKU 通用的 `missing_or_partial_inputs` 扣分。
- 缺失证据只影响依赖该证据域的购买理由。
- 真实冲突按命中的参数、卖点或评论主题作用于相关锚点。
- M12C 缠绕在具体卖点与购买理由上，不再作为所有锚点的全局门槛。
- 价格/WTP 类购买理由必须有 M12C，或同时具备明确价格位置、用户感知和市场承接；功能适配类购买理由可由参数、评论、场景和市场证据成立。
- 每个 SKU 最多保留 3 个 `core_payment`，同锚点族只保留证据最强者，其余降为 `supporting`。

### 7.5 画像状态与复核解耦

建议状态：

| 状态 | 定义 | 下游处理 |
| --- | --- | --- |
| `ready` | 至少 1 个核心成交理由，核心锚点置信度达标，无画像级阻断 | 可参与强锚点比较和竞品排序 |
| `ready_limited` | 有可用辅助理由，但核心理由证据不足，或相关证据域有限 | 可展示，不得形成强替代结论 |
| `weak_expression_only` | 只有厂家表达或弱证据，没有可用的核心/辅助成交理由 | 只展示证据不足，不进入锚点比较 |
| `missing_input` | 没有形成任何可用购买理由所需的最低输入 | 不参与锚点强比较 |
| `failed` | 运行失败或契约错误 | 阻断消费 |

`review_required` 改为独立字段，只在存在 `blocking` 问题或人工判断可能改变核心锚点时为真。提示和范围说明不触发人工复核。

## 8. 发布门槛

新 TV M12D 版本发布前必须同时满足：

| 指标 | 门槛 |
| --- | ---: |
| 生成成功率 | `>= 98%` |
| `ready` 占比 | `>= 85%` |
| `ready + ready_limited` 占比 | `>= 95%` |
| `review_required` 占比 | `<= 15%` |
| `missing_input + failed` 占比 | `<= 5%` |
| 核心成交理由缺失占比 | `<= 15%` |
| 重点验证 SKU 通过率 | `100%` |

新增系统性异常门槛：同一个 `blocking` 问题覆盖超过 20% SKU 时，判定为系统问题并阻断发布，不得把全部 SKU 推入人工复核队列。

按现有强度阈值进一步分层，影子结果预计为 332 个 `ready`、33 个 `ready_limited` 和 12 个 `weak_expression_only`，即 `ready + ready_limited` 为 365/377（96.8%）。这说明 85% 正常率和 95% 可用率门槛有现实基础；正式实现仍必须通过全量重跑和样本人工验收，不能直接把影子结果写入发布表。

## 9. 实施顺序

1. 修复 M03B 尺寸段等价规范化，并保存冲突参数、候选值和证据明细。
2. 为 M04C/M05C/M07/M09C/M10C/M11C/M12C 建立模块专用质量适配器，停止使用通用“有标记即 partial”。
3. 实现三轴质量模型、问题作用域和当前 serving scope 依赖重算。
4. 修改 M12D 锚点级评分、画像置信度、核心锚点去重与最多 3 个限制。
5. 增加影子运行和新旧差异报告，先验证重点 SKU，再全量运行 377 个 TV SKU。
6. 通过发布门槛后发布新版本，并弃用当前 100% `review_required` 的版本。
7. 最后让竞品分析消费新版本；竞品智能体不得补写 M12D 生产逻辑。
