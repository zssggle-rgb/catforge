# G08 产品经理业务语言独立评审

## 结论

`FAIL with one semantic blocker`。七列主表的整体结构已经能够回答产品经理的核心工作问题，且没有内部自证、购买前心智猜测或通用动作清单；但纯负向用户反馈被错误写成“正反并存”，在修复前不能作为可靠的 SKU 用户价值账上线。

## 结构对产品经理的实际帮助

| 主表字段 | 产品经理拿它做什么 |
| --- | --- |
| 价值战场及市场空间 | 判断这笔产品投入对应的是哪个用户比较场，以及该场是否值得进入产品价值结构 |
| 本品核心采购理由 | 看用户为什么把本品纳入选择，不再从技术参数反推理由 |
| 用户实际获得的价值 | 核对设计投入是否在购后形成真实体验，而不是只证明产品“具备能力” |
| 支撑卖点组合 | 看哪些配置必须作为一个组合共同解释，避免把共同变化的技术点重复计价 |
| 相对基础与同价值竞品 | 分清基础价值增量、同价值直接竞争和上探参照，知道比较结论来自哪类反事实 |
| 选择和价格兑现 | 分开看价值成立、选择关联、整机价格承接和严格市场隐含区间，不能量化不等于没有价值 |
| 产品角色 | 判断该组合是核心差异、同档门槛、辅助选择还是仅有配置支撑 |

这套结构的核心不是给产品经理一个自动动作，而是补上他现有途径拿不到的答案：用户购后实际感知到了什么价值，这个价值在市场选择和价格上最多兑现到哪一层。

## 已通过的业务语言门禁

1. 主表不出现 Mxx、Qx、isolation grade、SQL、evidence ID、relation hash 或英文错误码；
2. 不写“建议涨价/降价/增配/减配”，不生成下一步工作清单；
3. 不推测购买前宣传心智，只说明当前证据来自购后体验；
4. “用户价值是否成立”和“价值能否量化”分栏表达，金额为空不会被写成价值为零；
5. 共线卖点明确按组合判断，不拆成单项金额；
6. 市场隐含区间明确写成观察性市场承接，不冒充心理最高价或因果效应；
7. 短答、Markdown 和飞书卡片消费同一个 report object，采购理由和业务行保持一致；
8. `查看用户选择对比` 与 `查看分析依据` 是两个独立入口。

## 业务语义阻断项

### P01：纯负向体验被写成“正反并存”

当前 `_value_status()` 把 negative-only 和 positive+negative 都映射为 `conflicted`；`_confidence_label()` 再把所有 `conflicted` 写成“用户体验正反并存”。现有测试甚至用两条纯负向评论断言这句话。

这对产品经理不是小措辞问题：

- 纯负向代表“产品具备能力，但用户实际获得的是负向结果/价值未兑现”；
- 正反并存代表“不同用户或场景体验分化”；
- 事实版本冲突代表“数据不能判断”。

三者对应完全不同的产品判断，必须分开。修复建议是在 typed contract 中增加明确的 negative-only 状态或等价极性字段，并让 PM 文案分别输出“负向体验”“体验分化”“事实冲突”。

## 可读性改进项

1. “估算销量约 1,000 台”没有在同一单元格说明尺寸档和市场窗口，产品经理可能不知道这是全品类、目标尺寸还是当前观察期；修复时应把现有 `target.size_tier`、`market_window` 和平台覆盖翻译成简短范围说明；
2. “用户已实际感知到这项价值：用户购后反馈已观察到……”存在轻微重复，可压缩为一次结论加一次具体体验；
3. 这些改进不能自动生成定价或增减配动作，仍只改善可读性和口径。

## PM 准入决定

`G09 not allowed`。先修复 negative-only / mixed / lineage-conflict 三类状态，再用同一份正向、纯负向、正反并存和事实冲突 fixture 回放 JSON、短答、Markdown、飞书卡片。
