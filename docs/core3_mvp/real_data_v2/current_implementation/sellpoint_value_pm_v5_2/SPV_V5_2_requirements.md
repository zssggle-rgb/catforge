# 用户卖点价值画像 V5.2 需求

状态：SPV52-G01 已冻结

日期：2026-07-18

适用范围：TV、AC；按 `project_id`、`category_code`、`release_scope_key` 隔离

基线版本：用户卖点价值画像 V5.1

详细设计：`SPV_V5_2_detailed_design.md`

任务调度：`SPV_V5_2_goal_dispatch.md`

## 1. 本轮改造要解决什么

V5.1 已能形成用户价值、市场量价、投入分类和产品建议，但消费层仍存在一个会直接损害产品经理信任的问题：

> 系统把参数、能力名称或内部价值主题反向拼成“产品卖点”，导致产品经理看到自己没有写过的卖点。

典型错误包括：

- 把 `1920 分区`、`300Hz` 等参数直接当成产品卖点；
- 把“游戏与运动流畅”“明亮环境与明暗层次”等内部价值主题写入产品卖点栏；
- 原始卖点不存在时，用能力名称或参数拼接结果兜底；
- 把基础参数统一展示成基础卖点；
- 把“量子点”等技术路线直接写成卖点短板，没有先证明其对应的用户价值缺口。

V5.2 的目标是建立一套不可混写的用户卖点价值合同：

> 产品卖点必须来自产品已经写过的原始卖点；系统只负责识别它由哪些参数支撑、用户是否认知、形成了什么用户价值，以及市场是否承接。

## 2. 产品经理要得到什么

对每个 SKU，画像首先回答：

1. 产品实际写了哪些卖点；
2. 每个卖点由哪些参数或产品事实支撑；
3. 用户从该卖点中感知到了什么价值；
4. 该卖点属于核心卖点、基础卖点、用户未认知卖点还是待确认卖点；
5. 没有形成产品卖点的参数，哪些只是基础参数、哪些形成差异、哪些是参数短板；
6. 哪些竞品卖点构成本品机会，哪些只是非关键竞品卖点；
7. 产品经理应修改卖点表达、改善体验、维持基础配置，还是评估产品缺口。

产品经理看到的第一对象始终是自己熟悉的原始卖点，不是系统内部主题。

## 3. 四层业务对象

### 3.1 产品参数

产品客观具备的配置、档位和技术事实，例如：

- 1920 分区；
- 5200nits；
- 4K 170Hz 原生刷新；
- 四路 HDMI 2.1；
- 48Gbps。

权威来源为 M03B 参数事实画像及画像已保存的同源参数事实。参数不能自动变成卖点。

### 3.2 产品原始卖点

产品在输入资料中实际写过的宣传表达，例如：

> 4K 170Hz原生高刷+300Hz动态刷新，四路满血HDMI 2.1支持48Gbps传输，游戏影音双丝滑。

权威来源为 M04C 卖点事实：

- `source_claim_key`；
- `raw_claim_text`；
- `clean_claim_text`；
- `claim_code`；
- `claim_name`；
- `claim_fact_id`；
- `evidence_ids`；
- 参数支撑状态及参数代码。

没有 M04C 原始卖点引用的内容，不得进入“产品卖点”字段。

### 3.3 用户价值

用户在选择、使用和反馈中体现出的实际好处，例如：

- 游戏响应更快；
- 高速画面更流畅；
- 明亮环境画面清楚；
- 暗场层次更清晰、光晕更少。

用户价值来自已保存的评论、采购理由、用户价值和市场比较结果。它回答“用户感知到了什么”，不能反向冒充产品卖点。

### 3.4 内部价值主题

系统用于归组、比较和量化的分析维度，例如：

- 游戏与运动流畅；
- 明亮环境与明暗层次；
- 色彩与画面真实。

价值主题只用于内部聚合和分析。可以在审计下钻中显示为“内部价值主题”，不得作为产品卖点名称。

## 4. 产品卖点来源规则

### 4.1 唯一合法来源

进入本品卖点分类的每一条记录必须具备：

- 一个合法 M04C `claim_fact_id`；
- 一个 `source_claim_key`；
- 非空 `raw_claim_text`；
- 标准 `claim_code / claim_name`；
- 至少一个可回溯证据引用。

### 4.2 原文展示

- 报告必须保留原始卖点全文；
- 卡片可展示原文中的精确短句，但该短句必须是 `raw_claim_text` 的连续子串；
- 无法抽取精确短句时，使用标准卖点标签作为标题，并在下方展示原始卖点全文；
- 系统不得改写原文后再称其为“产品原始卖点”。

### 4.3 禁止兜底

以下内容禁止填充产品卖点字段：

- 参数名或参数值；
- capability 名称；
- value bundle 名称；
- battlefield 名称；
- topic/value theme 名称；
- LLM 或模板现场生成的卖点简称。

没有原始卖点时，明确保存 `no_source_sellpoint`，并将事实放入参数或用户价值账。

## 5. 分类体系

### 5.1 本品卖点分类

分类对象必须是有原始卖点来源的标准卖点事实。

| 分类 | 定义 | 产品经理处理原则 |
| --- | --- | --- |
| 核心卖点 | 原始卖点存在，产品事实成立，用户价值已形成，并获得相对市场表现支撑 | 重点传播并持续强化 |
| 基础卖点 | 原始卖点存在，但其主要支撑能力已是当前同尺寸、同价格层普遍要求 | 保持，但不单独承担差异化和溢价任务 |
| 用户未认知卖点 | 原始卖点和产品事实存在，但现有用户反馈尚未形成对应认知或体验价值 | 优先改体验或改表达，不继续堆同类参数 |
| 待确认卖点 | 原始卖点存在，但当前证据不足或存在局部冲突 | 明确标注待确认，不下产品取舍结论 |

### 5.2 参数分类

没有原始卖点映射的参数不得进入卖点分类。

| 分类 | 定义 |
| --- | --- |
| 差异化参数 | 具体参数档位与核心卖点及用户价值相连，并形成相对优势 |
| 基础参数 | 当前同尺寸、同价格层普遍具备，需要维持但不承担卖点任务 |
| 参数短板 | 本品缺失或档位较弱，且可比产品的用户价值或市场表现显示本品受压 |
| 非关键参数差异 | 竞品具备、本品缺少，但当前未形成可观察竞争损失 |
| 待确认参数 | 已知存在差异，但证据不足以判断业务影响 |

### 5.3 竞品卖点发现

竞品发现不混入“本品已有卖点”：

- `卖点机会`：竞品存在有来源的卖点，本品没有对应卖点或用户价值，并有竞争表现证据；
- `非关键竞品卖点`：竞品存在该卖点，但当前没有证据显示其造成本品竞争损失；
- 只有参数差异、没有竞品原始卖点或用户价值证据时，只进入参数分类，不能生成卖点机会。

## 6. 卖点、参数、价值映射

每个本品卖点评估必须保存：

1. 原始卖点引用；
2. 标准卖点标签；
3. 支撑参数列表；
4. 对应用户价值列表；
5. 内部价值主题代码；
6. 卖点分类；
7. 市场量价支撑；
8. 业务建议；
9. 证据边界与置信度。

同一原始卖点可以映射多个标准卖点事实。分类以 `source_claim_key + claim_code` 为最小单元，报告按原始卖点分组，不能为了显示方便强迫一个复合原始卖点只有一个分类。

## 7. table_stake 处理

`table_stake` 继续按同尺寸、同价格层判断；AC 额外使用安装方式等品类边界。

判断结果必须分流：

- 有原始卖点映射：进入“基础卖点”；
- 没有原始卖点映射：进入“基础参数”；
- 具体领先档位仍可单独进入“差异化参数”，不能被泛能力的基础属性覆盖；
- `not_assessed` 进入待确认参数，不触发整版 review；
- missing 不作 false。

## 8. 画像合同

V5.2 在现有 V5.1 JSON 画像合同中新增 typed sections，优先不新增数据库列：

- `source_sellpoint_facts`；
- `sellpoint_parameter_links`；
- `sellpoint_user_value_links`；
- `sellpoint_assessments`；
- `parameter_assessments`；
- `competitor_sellpoint_findings`；
- `layer_integrity_summary`。

input fingerprint 和 result hash 必须包含：

- M04C 卖点事实 profile/hash；
- M03B 参数事实 profile/hash；
- 用户价值和竞品画像来源版本/hash；
- 映射规则版本和分类规则版本。

旧 V5.1 画像保持只读，不原地补写、不改变 result hash。

## 9. 消费规则

报告、卡片和问答只消费画像中已保存的 V5.2 分层结果：

- 不现场读取 M04C；
- 不现场生成卖点名称；
- 不从 capability 或 value theme 反推卖点；
- 卖点区只展示有来源卖点；
- 参数区独立展示基础参数、差异化参数和参数短板；
- 内部价值主题默认不占用产品经理首屏；
- 审计下钻可查看完整来源、标准标签和内部主题；
- 正式消费在 V5.2 明确发布前继续使用 V5.1 current。

## 10. 65E7Q 首验标准

205 只生成 V5.2 draft，至少满足：

1. “游戏与运动流畅”不出现在产品卖点字段；
2. 游戏相关分类回溯到真实原始文案“游戏影音双丝滑”及其完整原文；
3. 170Hz、300Hz、HDMI 2.1、48Gbps 只作为支撑参数；
4. “用户未认知卖点”明确展示产品原始卖点、预期用户价值和当前用户认知；
5. 1920 分区、5200nits 等不能由程序重新拼成产品原始卖点；
6. MiniLED 等 table-stake 项有原始卖点时进入基础卖点，没有时进入基础参数；
7. “量子点”不得直接成为卖点短板；只有卖点、用户价值和竞争证据完整时才形成卖点机会；
8. 原有候选、用户价值、量价和价格支撑结论不得因本轮分层改造丢失；
9. 报告、卡片、问答使用同一画像 result hash；
10. 不 review、不 publish、不切 current。

## 11. TV/AC 完成定义

1. TV、AC 原始卖点读取覆盖率和缺失分布可审计；
2. 所有展示为产品卖点的内容均具有 M04C 来源，来源完整率 100%；
3. value theme 冒充产品卖点计数为 0；
4. 参数冒充产品卖点计数为 0；
5. 无原始卖点的 SKU 仍可输出参数账和用户价值账，但明确无本品卖点分类；
6. 65E7Q 和一个 AC SKU 先通过真实草稿验收；
7. 双品类通过后才允许生成 TV/AC 全量 V5.2 draft；
8. 完整回归、性能、方法/工程/业务评审集中执行一次；
9. publish/current 必须另行获得用户明确批准。

## 12. 明确不做

- 不修改 M04C、M03B、竞品画像或旧 M12/M13/M14 的已发布结果；
- 不重跑 M03B—M12D；
- 不用 LLM 重新撰写产品原始卖点；
- 不把价值主题改名后伪装成产品卖点；
- 不把单个参数直接升级为卖点机会；
- 不重做飞书卡片视觉样式；
- 不原地修改已发布 V5.1 画像；
- 不自动 review、publish 或切 current。
