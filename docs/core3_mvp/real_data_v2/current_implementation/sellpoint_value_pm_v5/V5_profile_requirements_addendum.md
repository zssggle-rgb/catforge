# 用户卖点价值分析 V5 画像化补充需求

状态：需求冻结候选

日期：2026-07-13

适用范围：TV、AC；按 `category_code`、`product_category` 严格隔离

上位需求：`V5_requirements.md`

详细设计：`V5_profile_detailed_design.md`

任务调度：`V5_profile_goal_dispatch.md`

需求追溯：`V5_profile_requirements_traceability.md`

## 1. 修订背景

现有 V5 已能在一次运行中读取 SKU 配置、宣传、用户反馈、采购理由、价值战场和市场量价，构造多类对照并生成产品经理报告，但仍存在五个产品缺口：

1. 候选快照被技术上限截断，固定数量被误当作候选竞品定义；
2. 同尺寸、同价格市场产品和真实竞品没有分开；
3. HDMI 2.1 等门槛功能仍可能被计入差异化用户价值；
4. 完整分析只存在于一次运行结果中，没有形成可版本化、可审核、可复用的 SKU 画像；
5. 报告渲染和后续问答无法稳定消费同一份已保存结论。

本补充需求把 V5 从“一次性报告生成器”升级为以下闭环：

```text
上游画像发布
  -> 生成完整竞品候选宇宙与分析参考池
  -> 生成 SKU 用户卖点价值画像草稿
  -> 质量校验与审核
  -> 发布画像
  -> 智能体读取同一画像生成报告
  -> 围绕同一画像继续深入问答
```

## 2. 产品目标

对每个 SKU 保存一份“用户卖点价值决策画像”，让产品经理和智能体能够稳定回答：

1. 哪些投入值得继续保留；
2. 哪些投入已经具备但没有转化成用户价值；
3. 哪些竞品配置不需要跟进；
4. 当前价格是否获得用户价值支撑；
5. 如果追求销量，需要改卖点、改价格，还是改变 SKU 角色。

画像既保存上述决策答案，也保存得出答案所需的完整分析事实、候选清单、问题级对照、证据、边界和版本。报告只负责组织语言，不得重新推导结论。

## 3. 核心概念修订

### 3.1 竞品候选宇宙

竞品候选不是固定 3 款、12 款或 20 款，也不是所有同尺寸产品。

竞品候选定义为：

> 用户购买目标 SKU 时，可能用于替代、比较、升档、降档或发生同品牌转移的全部产品。

权威来源为当前已发布或当前有效的 M12 候选召回与 M13 候选评分：

- M12 决定产品是否存在真实竞争关系以及关系来源；
- M13 决定产品在哪些竞争角色下可用，以及证据完整度；
- M14 只给其中的重点竞品增加优先级和角色标签，不限制候选宇宙数量。

候选宇宙数量等于当前 M12/M13 中满足条件的实际记录数，不设置业务数量上限。

### 3.2 分析参考池

分析参考产品不一定构成用户购买替代，只用于回答特定研究问题，包括：

- 参数不同取值的市场组；
- 高、低绩效市场原型；
- 相邻价值战场案例；
- 新产品形态或技术路线标杆；
- 市场合成基线供体。

分析参考池必须与竞品候选宇宙分开保存、分开命名。报告不得把参考产品写成“直接竞品”。

### 3.3 门槛功能

门槛功能是目标竞争范围内普遍具备、用户购买时默认要求但难以单独形成选择差异的能力。

门槛功能判断必须基于产品事实的已知样本普及率，不能使用“竞品没有对应评论”推断竞品不具备。缺失、空值和未知不进入“未具备”分母。

门槛功能仍可出现在产品配置说明中，但：

- 不计入差异化用户价值数量；
- 不单独支撑价格溢价；
- 不因目标 SKU 用户提到而自动成为亮点；
- 只有其形成的体验结果相对竞品更强时，体验结果才能进入差异化价值。

### 3.4 用户反馈覆盖

“用户反馈覆盖”不是评论数量、用户认可率或用户占比。

它表示：某项用户价值包含的可观察体验要点中，当前用户反馈画像已形成正向、负向、矛盾或未知证据的状态。

报告统一使用：

- `已形成正向反馈证据`；
- `已形成负向反馈证据`；
- `正负并存`；
- `现有反馈尚未覆盖`。

禁止把“未覆盖”写成“用户不认可”“竞品没有”或“反馈少”。

## 4. 竞品候选资格

### 4.1 允许进入的竞争关系

一款产品至少满足一种关系即可进入候选宇宙：

| 关系 | 业务含义 | 主要来源 |
| --- | --- | --- |
| 直接替代 | 用户、任务、采购理由、价值战场和价格均高度重叠 | M12/M13 direct fight |
| 同预算替代 | 用户在相近预算下会实际二选一 | M12 价格邻近、M13 price position |
| 降档分流 | 价格更低且基础价值足够，可能分流目标用户 | M13 price-volume pressure |
| 升档替代 | 价格更高但价值更强，可能吸引目标用户继续加价 | M13 benchmark/uptrade |
| 同品牌梯度 | 同品牌产品线内部存在升级、降级或蚕食关系 | M12 same brand、M13 role |
| 场景替代 | 技术路线不同但解决相同用户任务 | M12 scenario substitute |
| 同价值替代 | 宣传或承接相同用户价值，可比较兑现差异 | M12/M13 claim-value overlap |

尺寸、价格、品牌、参数相似度都是竞争关系证据，不是单独的竞品定义。

### 4.2 候选状态

每个候选保存以下状态：

- `eligible`：可用于至少一个正式比较问题；
- `limited`：只能用于部分问题，必须记录可用范围；
- `review_required`：保留在画像和审核队列，不得驱动确定结论；
- `blocked`：仅留审计，不参与业务计算；
- `recalled_only`：M12 已召回但 M13 尚未完成，不参与高置信结论。

低置信候选不得被隐藏，也不得与有效候选混算。

### 4.3 数据可用范围

候选不是“全部数据都齐全才进入”。每款候选按问题记录可用性：

- 有市场量价，可用于价格和销量问题；
- 有参数事实，可用于能力和门槛功能问题；
- 有宣传与用户反馈，可用于价值兑现问题；
- 有采购理由和价值战场，可用于替代关系问题；
- 数据不齐的维度保持 unknown。

### 4.4 缺少 M12/M13 时的处理

若目标 SKU 没有当前有效 M12/M13 候选：

- 不得把同尺寸市场全量自动改名为候选竞品；
- V5 画像标记 `competitor_universe_status=unavailable`；
- 同尺寸市场产品只可进入分析参考池；
- 依赖竞品关系的结论为空或降级；
- 画像仍可保存已完成的产品事实和用户价值分析。

## 5. 候选使用规则

### 5.1 完整保存、按题选用

画像保存全部候选，但每个问题只选择满足该问题条件的候选：

| 产品问题 | 使用候选 |
| --- | --- |
| 当前价格是否合理 | 全部有效同预算替代候选 |
| 某项价值是否形成优势 | 全部有效同价值候选 |
| 产品线角色是什么 | 全部有效同品牌梯度候选 |
| 为什么没有获得更大销量 | 全部有效降档分流和价格更低、销量更高候选 |
| 哪个配置不需要跟 | 具备该配置且构成真实替代的候选 |
| 某参数是否转化成价值 | 分析参考池中同一参数不同有效取值组 |
| 是否能进入相邻战场 | 分析参考池中的相邻战场标杆，不冒充竞品 |

计算不设候选数量上限；产品经理报告可只展示代表产品名称，但必须同时展示实际样本数，并允许下钻完整清单。

### 5.2 完整候选的加载方式

“不设业务数量上限”不等于一次加载所有候选的完整评论证据。

- 候选 manifest 全量加载并保存；
- 市场、参数、角色等结构化摘要按列批量加载；
- 完整评论原文和证据详情按问题、按下钻延迟加载；
- 不得用内存上限改变候选业务定义；
- 查询、内存和报告长度限制只能改变加载方式或展示数量。

## 6. 门槛功能过滤

### 6.1 判断顺序

对每项能力依次判断：

1. 目标 SKU 是否确认具备；
2. 有多少有效候选的该能力事实为 known；
3. known 候选中的具备率；
4. 在当前尺寸、价格带、价值战场或竞争角色内是否普遍；
5. 产品能力虽普遍，是否形成了不同的用户体验结果；
6. 不同体验结果是否有价格、销量或选择表现支持。

### 6.2 可配置门槛

门槛不得写死在报告代码中。按品类配置：

- 最低 known 样本数；
- 候选普及率阈值；
- 价格带或产品形态分层；
- 允许保留为差异化的体验结果；
- 缺失值处理方式。

默认建议值仅作为实现起点：known 候选不少于 5，事实普及率不低于 80%。最终阈值必须通过 TV、AC 真实样本验收后冻结。

### 6.3 投入分类

每项产品投入必须归入以下一种：

| 分类 | 产品事实 | 用户感知 | 竞品差异 | 产品经理含义 |
| --- | --- | --- | --- | --- |
| `retain` | 具备 | 已形成 | 有差异且量价支持 | 值得保留 |
| `unconverted` | 具备 | 尚未覆盖/较弱 | 竞品已形成或投入较高 | 先提高体验兑现，不继续堆参数 |
| `do_not_follow` | 不具备 | 不影响当前竞争 | 竞品具备 | 当前无需跟进 |
| `table_stake` | 具备 | 可有反馈 | 市场普遍具备 | 保持门槛，不作为核心溢价卖点 |
| `missing_competitive_gap` | 不具备 | 对照显示影响选择 | 竞品具备且表现更好 | 产品定义优先补齐 |
| `unknown` | 未知/冲突 | 未知 | 不可比较 | 不下结论，进入审核 |

分类必须保存理由、对照候选、证据和限制，不能只保存标签。

## 7. SKU 用户卖点价值画像

### 7.1 画像定位

画像是报告和深入问答的唯一业务事实来源。它不是渲染后的文章，而是可验证、可查询、可版本化的业务 DTO。

建议 schema：`sku_sellpoint_value_decision_profile_v1`。

### 7.2 版本级记录

版本记录至少包含：

- `project_id`、`category_code`、`product_category`、`batch_id`；
- `profile_version`、`schema_version`、`rule_version`；
- `release_status`、`release_quality_status`、`is_current`；
- 生成、审核、发布、废弃时间和操作者；
- 上游版本范围、SKU 数量和质量统计；
- `input_fingerprint`、`candidate_manifest_hash`、`result_hash`。

### 7.3 SKU 主画像

每个 SKU 至少保存：

- 目标 SKU 身份与市场摘要；
- 上游画像状态和 source lineage；
- 全量竞品候选 manifest；
- 全量分析参考 manifest；
- 门槛功能判断结果；
- 一行一个“价值战场 × 用户价值组合”的价值账；
- 问题级反事实选择与量价结果；
- 产品投入分类；
- 当前价格与销量角色；
- 已有战场增强和新战场拓展判断；
- 五个产品经理答案；
- 可问答主题索引；
- 证据摘要、限制、质量状态和 hash。

### 7.4 候选明细

每个候选保存：

- SKU、品牌、型号；
- M12 召回关系和来源；
- M13 组件分数、角色分数和可用问题；
- M14 重点竞品标签（若有）；
- 价格、周均销量、价格带、尺寸/形态；
- 参数、宣传、反馈、采购理由和战场数据状态；
- 候选状态、审核状态、风险和证据 hash；
- 被哪些问题选中以及选择原因。

### 7.5 用户价值明细

每项用户价值保存：

- 价值战场、采购理由、用户价值和场景结果；
- 能力组合与宣传卖点；
- 各能力的投入分类；
- 用户反馈证据状态；
- 对照问题、候选集合和比较结果；
- 价格承接、销量承接和边界；
- 代表证据引用和结果 hash。

### 7.6 建议物理模型

至少新增：

1. `core3_sellpoint_value_profile_version`：画像版本与发布状态；
2. `core3_sku_sellpoint_value_profile`：SKU 主画像及决策 JSON；
3. `core3_sku_sellpoint_value_candidate`：完整竞品/参考候选 manifest；
4. `core3_sku_sellpoint_value_item`：价值战场 × 用户价值组合明细。

详细证据原文继续引用上游 evidence，不复制工厂内部原始模板或 prompt。

## 8. 画像生成与发布生命周期

### 8.1 生成触发

支持两类触发：

- 单 SKU 显式生成：用于调试、预览和深入分析；
- 版本级批量生成：上游权威画像发布后，为全部有效 SKU 生成新画像草稿。

以下任一输入变化必须使 input fingerprint 变化并生成新草稿：

- M03B 参数画像；
- M04C 宣传与 claim 事实；
- M05C 用户反馈画像；
- M07 市场量价；
- M09C/M10C 用户任务和目标群体；
- M11C/M11D 价值战场和销量分配；
- M12D 采购理由；
- M12/M13/M14 竞品候选与角色；
- 门槛功能配置和 V5 方法版本。

### 8.2 幂等与历史版本

- 相同 input fingerprint 重跑不得产生语义不同结果；
- 相同 profile version + SKU 只能有一个当前草稿；
- 新草稿不得原地覆盖已发布画像；
- 发布新版本时才切换 current published；
- 历史画像和候选 manifest 必须可回读；
- 画像回读后必须通过 Pydantic schema 校验和 result hash 校验。

### 8.3 审核与发布

生成、审核、发布必须分离：

```text
generated draft
  -> auto validation
  -> auto_pass / review_required / blocked
  -> human review when required
  -> published current
```

报告默认消费 current published 画像。显式 preview 才能消费 draft，并必须展示草稿状态。

低置信、线谱冲突、竞品宇宙缺失、门槛样本不足和价格结论越界必须进入 review reason。

## 9. 智能体消费画像生成报告

### 9.1 单一数据源

JSON、短答、Markdown、飞书文档和卡片必须从同一个已保存画像生成。渲染器不得重新查询市场、重新选择候选或计算新的结论。

报告必须展示所消费的：

- profile version；
- release status；
- generated/published time；
- candidate manifest hash；
- result hash。

### 9.2 第一屏五个答案

第一屏固定回答：

1. 值得继续保留的投入；
2. 已投入但未转化的能力；
3. 不需要跟进的竞品配置；
4. 当前价格是否获得价值支撑；
5. 追求销量应改卖点、改价格还是改变 SKU 角色。

每个答案必须引用画像中的具体价值项、候选集合和量价证据，不输出通用工作建议。

### 9.3 下钻内容

报告允许下钻：

- 全量候选及角色；
- 某项投入为何被分类；
- 某个量价数字来自哪个候选集合；
- 哪些结论因缺失或门槛过滤未输出；
- 与上一画像版本相比发生了什么变化。

## 10. 基于画像的深入问答

### 10.1 问答原则

深入问答必须锁定报告使用的同一 profile version，不能在回答过程中静默重跑分析或切换候选集合。

每个回答由四部分组成：

1. 直接业务答案；
2. 使用的画像事实和问题级对照；
3. 对产品工作的含义；
4. 当前证据边界。

### 10.2 必须支持的问题

- 为什么这项投入值得保留？
- 为什么该配置已经具备但用户没有感知？
- 为什么某个竞品配置不用跟？
- 当前价格为什么算获得支撑？
- 降价是否会增加销量，能增加多少？
- 如果要走量，应该改卖点还是改价格？
- 与某个指定竞品相比，本品赢在哪里、输在哪里？
- 哪些结论来自竞品候选，哪些来自分析参考池？
- 为什么某款产品被选为这个问题的对照？
- 候选产品变化后，结论发生了什么变化？

### 10.3 问答边界

- 画像没有保存的结论不得临时推断成确定答案；
- 允许从画像已有事实组合解释，但必须返回使用的字段和候选集合；
- 精确降价增量只在自身价格曲线或合格准实验存在时回答；
- 缺少成本数据时不回答利润和 ROI；
- 不把门槛功能写成差异化价值；
- 不把分析参考产品写成竞品；
- 画像过期或上游版本已变化时提示 stale，不静默使用新旧混合数据。

### 10.4 问答接口产物

画像应生成可检索问答索引，至少包括：

- `topic_code`；
- `question_patterns`；
- `answer_fact_paths`；
- `candidate_scope_ids`；
- `value_item_ids`；
- `evidence_refs`；
- `answer_boundary`。

智能体读取索引定位画像字段，再生成自然语言回答；测试中使用确定性规则或 mock，不调用外部 LLM。

## 11. 功能需求

- PF01：从 M12/M13 读取目标 SKU 全部当前候选，不设置业务数量上限。
- PF02：关联 M14 重点竞品标签，但不以 M14 Top 3 截断候选。
- PF03：竞品候选宇宙和分析参考池分离保存。
- PF04：每个问题从完整候选宇宙选择自己的候选集合，保存选择与拒绝原因。
- PF05：同尺寸价格池只能作为召回/参考来源，不能自动成为竞品宇宙。
- PF06：全量候选使用轻量 manifest，证据详情延迟加载，性能限制不得改变业务集合。
- PF07：基于产品事实 known 样本执行门槛功能过滤，missing 不作 false。
- PF08：生成 retain、unconverted、do_not_follow、table_stake、missing_competitive_gap、unknown 分类。
- PF09：一项投入只能有一个当前分类，分类变化必须可追溯。
- PF10：保存版本记录、SKU 主画像、候选明细和用户价值明细。
- PF11：画像包含 TV/AC category isolation、source lineage、confidence、review status 和 hash。
- PF12：支持单 SKU 生成和版本级全量生成。
- PF13：生成新草稿不覆盖 published current；发布与 current 切换独立执行。
- PF14：报告只读取画像，不重新计算候选、门槛或量价结论。
- PF15：短答、Markdown、飞书和卡片消费同一 profile DTO。
- PF16：支持按画像 topic 和字段路径进行深入问答。
- PF17：问答锁定 profile version，并返回事实路径、候选范围和边界。
- PF18：支持画像版本 diff，输出候选、投入分类、价格角色和五个答案的变化。
- PF19：画像缺失、过期、冲突或 blocked 时诚实降级，不回退到临时无版本计算。
- PF20：保留 V5 显式启用边界；画像生产、预览、发布和消费使用不同命令或参数。

## 12. 非功能需求

### 12.1 性能

- 候选数量不设业务上限；
- 禁止逐候选 N+1 查询；
- 全量 manifest 与结构化摘要批量读取；
- 完整评论证据按下钻加载；
- 目标性能在真实最大候选 SKU 上单独验收，不用截断集合换取通过。

### 12.2 确定性

- 候选 manifest 排序、问题级选择和 hash 必须确定；
- 输入顺序变化不得改变结果；
- 同一 input fingerprint 重跑 result hash 一致；
- 测试不得依赖外部 LLM。

### 12.3 可审计性

- 每个 PM 结论可追到画像字段、候选集合和上游 evidence；
- 门槛功能普及率保存 known、present、missing 数量；
- 每个候选保存进入和未进入具体问题的原因；
- 画像和报告不得复制 prompt、Gold Set 或工厂内部生成方法到运行时导出。

### 12.4 安全与发布

- 数据库迁移必须可回滚；
- 发布操作不得原地改写已发布画像；
- 多任务并发生成相同 version + SKU 时保持幂等；
- 失败只影响对应 SKU 草稿，不切换 published current。

## 13. 65E7Q 验收样例

使用 205 当前发布画像重新生成 65E7Q 时，至少验证：

1. 候选数量等于当前 M12/M13 有效候选数量，不固定为 12；
2. M14 重点竞品只作为标签，不改变候选总数；
3. 竞品候选和参数/市场参考产品在画像中分开；
4. HDMI 2.1 等高普及能力在门槛条件满足时归为 table stake；
5. 1920 分区能力已确认但现有用户反馈未形成分区控光价值时，归为 unconverted，而不是继续建议堆分区；
6. 量子点能力不具备，但同预算竞争仍有量价优势时，可归为 do_not_follow，且保存具体对照；
7. 当前同预算价格承接与低价走量价格带距离分别保存，不写成“降价必然增量”；
8. 画像保存“保持溢价角色”和“追求走量需改变价格带/角色”的决策边界；
9. 数据库回读画像后 result hash 与生成结果一致；
10. 报告从回读画像生成，与生成阶段报告内容一致；
11. 深入询问“为什么量子点不用跟”“降价会不会多卖”“为什么分区没有形成价值”时，回答引用同一画像版本和具体字段；
12. 上游候选、市场价格或用户反馈变化后生成新草稿，旧 published 画像保持可回读。

## 14. 明确不做

- 不把同尺寸市场全量定义为竞品；
- 不设置固定竞品数量；
- 不因报告版面限制截断计算候选；
- 不用评论是否提及判断产品是否具备功能；
- 不把门槛功能数量作为价值优势；
- 不在问答时静默重跑或换用新候选；
- 不让渲染器自行推导新业务结论；
- 不自动发布未审核画像；
- 不把 draft 原地改成 published；
- 不在缺少自身价格曲线时回答精确降价销量；
- 不把参考产品写成直接竞品；
- 不暴露工厂 prompt、Gold Set 或内部生成方法。

## 15. 完成定义

本补充需求只有同时满足以下条件才算完成：

1. 候选竞品宇宙来自全部当前 M12/M13 有效候选，且无固定数量截断；
2. 竞品候选和分析参考池在 schema、数据库和报告中明确分离；
3. 门槛功能过滤通过 TV、AC 真实样本验收；
4. 用户卖点价值画像具有版本、SKU、候选和价值明细的持久化合同；
5. 草稿、审核、发布、current 和历史版本语义正确；
6. 报告只消费数据库回读画像；
7. 智能体可围绕同一画像深入问答，并返回事实路径和边界；
8. 单 SKU 和版本级批量生成均可用且幂等；
9. 缺失、冲突、低置信和 stale 状态不被静默掩盖；
10. 65E7Q 和 AC 代表 SKU 在 205 完成生成、保存、回读、报告、问答和版本变化验收；
11. 相关单元、schema、migration、repository、service、CLI/API、回归和边界测试通过；
12. V5 默认关闭和工厂/运行时边界不回归。
