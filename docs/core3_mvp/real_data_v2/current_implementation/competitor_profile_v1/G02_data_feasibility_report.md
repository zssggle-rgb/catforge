# 竞品画像 V1 G02 数据可行性报告

状态：completed

日期：2026-07-14

环境：`deploy@123.56.42.205` / CatForge API 容器

方式：通过容器 stdin 执行 `G02_readonly_probe.py`，事务首句为 `SET TRANSACTION READ ONLY`，结束后 rollback。

## 1. 结论

新版画像可以支撑 TV 377 款和 AC 155 款生成竞品画像草稿，不需要先补跑旧 M08—M14。

但“能够全量召回候选”不等于“全部候选都是正式竞品”。当前任一单独语义来源都可能非常宽，尤其是共享核心采购理由：若直接并集，TV 的 broad union 候选中位数达到 317 款，AC 达到 142 款。因此 G03 必须设计候选资格门槛，禁止把市场池、共享任务、共享客群、共享战场或共享采购理由中的任一单项直接升级为正式竞品。

正确的数据结论是：

1. 每个 TV/AC SKU 都有 M03B、M07 和已发布 M12D，可生成基础竞争画像；
2. 评论、语义和 M12C 缺失只限制对应问题，不阻断整个 SKU；
3. 全部 TV/AC SKU 都能从至少一个来源召回候选；
4. 正式竞品资格必须由购买池门槛、多个独立关系证据和问题级数据可用性共同决定；
5. 现有数据需要 serving scope 合并和精确 rule/taxonomy 锁定，不能只按单个 batch 或 `category_code` 读取。

## 5. 品类与版本隔离

M04C、M05C、M09C、M10C、M11C、M11D、M12C、M12D 当前记录中，`product_category <> category_code` 均为 0。

但 M03B 历史表存在：

- `category_code=TV`；
- `rule_version=m03b_ac_param_profile_v0.1`；
- 155 行、155 个 SKU。

精确锁定 TV `m03b_tv_param_profile_v0.2` 和 AC `m03b_ac_param_profile_v0.2` 后，正确覆盖仍为 377/155。G04/G09 必须把以下条件写入读取合同：

1. project；
2. category；
3. product category（表具备时）；
4. SKU 前缀或主数据归属；
5. rule version；
6. taxonomy version；
7. published/current 或显式 preview version；
8. serving scope 中允许的 source batch IDs。

任何一个条件都不能用“取最新一行”替代。

## 6. Serving scope

AC 当前所有主要画像来自单一批次 `m00_20260624000202_1150a669`。

TV 当前画像跨三个 source batch：

- `m00_20260623014631_c8630747`；
- `m00_20260619084551_857df63b`；
- `m00_20260613004311_d548f6dc`。

因此竞品画像版本必须保存 source batch 列表和 serving scope，不能用某个 storage batch 等同于全部业务输入范围。

## 7. G03 方法设计准入条件

G03 必须解决：

1. 市场池、任务、客群、战场、采购理由均只是召回来源；
2. 正式候选至少通过购买池门槛，或通过明确的升档、降档、同品牌、场景关系门槛；
3. 共享通用采购理由不能单独成立同价值替代；
4. 直接替代必须包含购买池和至少两类独立价值/语义证据；
5. 降档分流必须证明基础用户价值仍可承接，不能只看低价高销量；
6. 升档替代必须证明价值增强与目标用户可达，不能只看价格更高；
7. 缺失模块按问题降级，不阻断基础竞品画像；
8. 全量 broad manifest 与正式 eligible relations 分开保存；
9. 候选数量限制只能用于分页和展示，不得改变业务集合；
10. TV 多批次 serving scope 与 AC 单批次 scope 使用同一版本合同表达。
