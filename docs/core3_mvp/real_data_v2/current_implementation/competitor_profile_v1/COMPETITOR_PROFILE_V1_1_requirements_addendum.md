# CatForge 竞品画像 V1.1 不降级分析需求补充

状态：G27 已冻结

日期：2026-07-15

## 1. 修改目标

V1.1 不推翻 V1 已完成的权威输入、全量候选宇宙、关系资产、版本状态机、批量生成和证据追溯。V1.1 只解决两个已确认的产品缺口：

1. V1 在生成过程中计算了参数、卖点、语义、采购理由、用户兑现和量价等双边结果，但最终画像只保存了压缩后的状态、编码和简化结论，不能完整支撑现有竞品分析智能体；
2. V1 把候选资格、上游复核、关系成立、问题可用和重点选择串成了逐层收紧的全局门槛，导致现有竞品分析智能体能够形成的有效比较，在画像中被整体降为 `review_required`、`reference_only` 或不可用。

V1.1 的产品目标是：

> 对每个目标 SKU 和候选 SKU，稳定保存现有竞品分析智能体能够计算出的多维比较过程、分维度结果、综合判断和证据边界；竞品分析智能体改为读取这些画像数据，不再现场重新召回和计算。

## 2. 产品边界

### 2.1 竞品画像负责

- 锁定目标 SKU、候选宇宙和权威输入版本；
- 计算并保存每个 target×candidate 的购买池、语义重合、价值锚点、替代压力、配置与卖点差异、用户兑现和市场表现；
- 保存每个维度使用了什么输入、如何计算、得到了什么结果、能支持什么结论、不能支持什么结论；
- 形成候选的竞争角色、重点程度、入选与未入选原因；
- 形成目标 SKU 的综合竞争结论；
- 提供稳定、版本化、可追溯的智能体读取合同。

### 2.2 竞品分析智能体负责

- 解析用户问题和目标 SKU；
- 一次读取指定竞品画像版本；
- 根据用户问题选择画像中的相应维度和结论；
- 组织业务语言、卡片、报告和深入问答。

### 2.3 竞品画像不负责

- 飞书卡片颜色、版式或组件；
- 报告目录和具体文案；
- 问答话术和展示长度；
- 在消费时重新召回、重算、补数、改分或重排候选；
- 为了适配某一种展示格式复制展示层字段。

## 3. 不降级基线

V1.1 以当前 `competitor-set` 和 `competitor_answer` 已实际使用的数据能力为最低基线。画像必须提供等价或更完整的数据，至少包括：

1. 目标和候选的产品身份、尺寸/能力段、价格带、均价和周均销量；
2. 候选进入购买池或分析范围的来源和原因；
3. 购买池层级、得分、预算关系和成立原因；
4. 价值战场、用户任务、目标客群双方条目、角色、交集、差集、加权重合得分和风险扣减；
5. 参数、卖点、卖点位置的双方实际值、共同项、本品独有、候选独有和重合得分；
6. 目标和候选的采购理由、关键价值锚点、用户兑现和购买阻力，包括 M12C `claim_values`、`estimated_contribution`、`pool_effect`、`context`、`scorecard`，以及 `claim_contribution` 的 attributions、positive claims、SKU gap 和 confidence；
7. 共同锚点、本品更强锚点、候选更强锚点、弱表达锚点、主张未兑现锚点和逐锚点匹配明细；
8. 价值锚点可替代性得分、等级和结论；
9. 主替代压力、辅助压力、压力组成、得分、等级和结论；
10. 市场验证强度、双方量价、差值、倍数、市场位置和可比边界，包括完整共同窗口快照、总体与共同窗口周均量、gap、ratio 和 boundary；
11. 每个分析维度的得分、总分、竞争角色和排序依据，包括 `recall_rank`、旧链 `competitor_score`、语义/参数卖点/销量接近度分项以及稳定排序字段；
12. 候选可支持的产品问题、结论强度、复核事项和证据引用；
13. 目标 SKU 的重点竞品、竞争优势、容易被替代的价值、配置差异和价格销量压力。

V1.1 不要求画像复刻展示文案，但要求画像数据能够让现有智能体在不访问原始分析原子的情况下生成同等信息密度的结果。

## 4. 多维分析结果合同

### 4.1 目标 SKU 分析快照

每个画像版本中的 SKU 必须保存一份可复用分析快照，至少包括：

- 产品身份、品类、品牌、型号和关键规格；
- 参数事实和具体档位；
- 卖点事实、卖点位置和参数支撑；
- 主、辅、机会、用户观察和拖累价值战场；
- 主、辅、机会和不足用户任务；
- 主、辅和机会目标客群；
- M12C 卖点价值角色与市场表现摘要；
- M12D 核心采购理由、价值锚点、用户兑现、购买阻力和成立状态；
- M07 均价、周均销量、销额、价格/销量分位和分析窗口；
- 各模块 availability、authority、lineage、review 状态和 evidence refs。

同一 SKU 快照在同一画像版本内只保存一次，不在每个 pair 重复保存。

### 4.2 Pair 分析过程

每个 target×candidate 必须保存以下过程数据：

| 维度 | 必须保存的过程 |
| --- | --- |
| 候选来源 | 全部 recall source、召回事实、候选范围角色 |
| 购买池 | 四类 gate 的输入事实、known/pass、层级、得分、预算差和原因 |
| 价值战场 | 双方条目与角色、主辅机会重合、错位、独有项、加权交并集、风险扣减 |
| 用户任务 | 双方主辅机会任务、重合和差异、加权得分 |
| 目标客群 | 双方主辅客群、重合和差异、加权得分 |
| 参数卖点 | 双方真实值、matched/target-only/candidate-only、基础项标记、重合得分 |
| 采购理由 | 双方角色和强弱、共同理由、不同路线、冲突和 lineage |
| 用户价值 | 采购理由、卖点价值、用户兑现、能力表达各层比较 |
| 价值锚点 | 共同/本品更强/候选更强/弱表达/主张未兑现、15 分制结果和明细 |
| 替代压力 | 主压力、辅助压力、组成项、10 分制结果、对成交的影响 |
| 市场验证 | 双方均价、周均销量、差值、倍数、分位、验证等级和可比边界 |
| 综合判断 | 分维度得分、总分、竞争角色、排序依据、结论强度和限制 |

参数卖点维度还必须保存 `fact_claim_codes`、supported/contradicted/unsupported 状态。市场验证维度必须保存 method、window、overlap weeks、target/candidate overall weekly volume、target/candidate overlap weekly volume、volume gap、ratio 和 boundary。上述字段不得在 adapter 或智能体消费时补算。

每个配置项必须标记：

- `feature_market_status=foundational|differentiating|unknown`；
- prevalence numerator、denominator、ratio 和来源；
- 双方原始参数差异。

基础功能的原始差异继续保存，但不进入差异得分、重点理由或产品跟进建议。HDMI 2.1 等高普及功能必须有专门回归样例。

### 4.3 Pair 分析结论

每个 pair 必须分别保存：

- `comparison_roles`：直接竞争、价格贴身、低价分流、升档替代、同品牌梯度、场景替代、同价值替代、配置标杆、市场参照，可多选；
- `primary_role` 和辅助角色；
- `dimension_conclusions`：每个维度保存机器可读结论和中文审计摘要；
- `overall_conclusion`：该候选如何影响目标 SKU 的机器可读综合结论和中文审计摘要；
- `business_questions`：可回答和不可回答的问题；
- `conclusion_strength`：`strong`、`supported`、`directional`、`reference`、`unknown`；
- `review_items`：需要复核的具体维度和原因；
- `limitations`：不能扩大的解释边界；
- `evidence_refs`、input fingerprint 和 result hash。

机器可读结论至少包含 `conclusion_code`、subject、direction、metrics、supporting fact refs、strength 和 limitations。中文文本仅用于审计和下游表达参考，不得成为画像唯一结论。

## 5. 门槛重构

### 5.1 门槛不再决定候选是否存在

只有下列机器枚举可以全局排除候选：

- `self_pair`：target 与 candidate 相同；
- `project_mismatch`：跨 project；
- `category_mismatch`：跨品类；
- `candidate_outside_manifest`：候选不在锁定的权威 SKU manifest；
- `identity_decode_failed`：输入损坏且无法识别产品身份。

authority 缺失、taxonomy unknown、source lineage 缺失或同 scope 冲突，在产品身份已知时必须继续分析，并把问题落到相应维度的 availability/review overlay，不得改写为新的 hard exclusion。

产品形态、尺寸、价格、任务、采购理由、用户兑现或参数缺失只能影响相应维度，不能全局阻断其他维度。

### 5.2 四个状态轴必须分开

V1.1 不再用一个 `candidate_status` 同时代表全部业务含义。必须分别保存：

1. `scope_status`：候选是否属于合法分析范围；
2. `dimension_availability`：各维度为 `available`、`partial`、`unknown` 或 `conflict`；
3. `conclusion_strength`：该结论能写到什么强度；
4. `review_required`：是否需要人工复核，作为叠加标记而不是全局禁用开关。

旧 `eligible/limited/review_required/reference_only` 字段在迁移期保留用于兼容，但不得再作为智能体读取和重点分析的唯一入口。

### 5.3 复核不得跨维度传播

- M05C 需要复核，只降低用户兑现结论，不得删除量价、参数、任务或战场结果；
- M12D 需要复核，只降低采购理由和价值锚点结论，不得删除价格贴身、配置标杆或市场分流结论；
- 战场角色冲突，只标记相关战场，不得让该候选全部七类关系变成 `review_required`；
- 某一关系不成立，不影响其他关系和其他问题继续计算；
- `review_required=true` 的候选仍可输出事实、方向性结论和明确复核事项，不得统一变成“无结论”。

### 5.4 问题级最低证据

| 产品问题 | 最低可用证据 | 不允许的扩大解释 |
| --- | --- | --- |
| 谁进入同一购买选择 | 购买池 + 至少一个语义/采购理由重合 | 只有同尺寸或同价不能写直接选择 |
| 谁形成价格销量压力 | M07 可比量价 + 合法候选范围 | 不能自动归因于单个卖点 |
| 哪些价值容易被替代 | 至少一层共同采购理由/用户价值 | 缺少用户兑现时只能写表达或方向 |
| 哪些配置值得关注 | 真实参数/卖点差异 + 至少一个价值/任务/市场关联 | 对方具备本品不具备不能自动要求跟进 |
| 谁是场景或产品线参照 | 场景任务或同品牌梯度事实 | 不得冒充直接二选一 |
| 谁进入重点名单 | 至少能独立回答一个产品决策问题 | 不得因其他维度未知而整款淘汰 |

### 5.5 得分与缺失处理

- 已知维度使用冻结权重计算；
- 未知维度不按 0 分处理，必须显示 `unknown`；
- 综合分必须同时保存 `raw_score`、`available_weight` 和 `normalized_score`；
- `available_weight` 仅用于解释覆盖和归一，不设置任何可阻止保存、问题参与或重点选择的最低值；
- 结论强度按问题直接所需事实判定：成熟计算器允许强结论且关键事实已知为 `strong`；正常完成且只有非关键缺失为 `supported`；至少一个直接相关维度已知为 `directional`；只能提供事实参照为 `reference`；全部直接相关维度未知才为 `unknown`；
- 任何非 `unknown` 的问题结论均可参与相应问题的比较和重点选择；
- 不允许通过提高统一门槛减少候选数量；性能问题必须由批量读取、共享快照和存储压缩解决。

## 6. 重点竞品与完整候选的关系

- 全量候选、可分析候选、正式竞争角色和重点竞品是四个不同概念；
- 重点竞品是画像计算结果，不是展示层临时排序；
- 当前竞品分析智能体能够计算并进入 Top 3 的候选，必须进入 V1.1 的可分析候选和重点选择计算；
- 候选未进入重点名单必须有具体原因：信息重复、综合影响较弱、只回答专项问题或证据覆盖不足；
- 不得使用“需要复核”“不是正式直接竞品”作为不继续计算其他维度的通用理由；
- 新方法允许因候选宇宙更完整而得到不同重点名单，但差异必须来自保存的计算结果和可解释方法，不能来自缺字段或全局门槛。

## 7. 智能体消费合同

竞品分析智能体读取 V1.1 后：

1. 只做 SKU 解析、问题路由、画像读取和语言组织；
2. 不调用 `same_size_price_candidates`、`semantic_overlap`、`param_claim_overlap`、`sales_overlap`、`sku_claim_value`、`claim_contribution`、价值锚点、替代压力、购买压力、综合打分、角色分配、排序或 Top 3 选择等任何现场分析函数；
3. 不改变画像保存的候选、维度得分、竞争角色、结论强度和重点顺序；
4. 允许按用户问题读取不同维度，但必须锁定同一画像版本；
5. 画像缺少整个 SKU 时明确返回画像不可用，不静默回退旧链；
6. 画像某个维度未知时只对该维度降级，其他已知结论继续回答；
7. 只能调用纯展示入口；测试中任何分析、角色、排序或选择函数被调用都必须立即失败。

## 8. 版本与迁移

- V1.1 使用新的 schema/rule/method/config 版本；
- V1 已保存 draft 保留只读，不原地改写；
- V1.1 从同一套 published/current M03B—M12D 重新生成新 draft，不重跑上游画像；
- 新增字段或表必须有 upgrade/downgrade、约束和数据保留测试；
- V1 历史行和旧约束保持兼容，但旧 `candidate_status`、旧 relation `review_required` 状态和旧 selected check 不得参与 V1.1 的候选保存、关系状态或重点选择；
- V1.1 使用版本条件约束：relation status 只允许 `passed|limited|unassessable|failed`，review 独立叠加；version 与 snapshot 的 scope 使用复合外键保证一致；downgrade 把 V1.1 version、snapshot 或分析列值视为阻断，但旧 V1 草稿不得阻断回退；
- V1 和 V1.1 reader 必须可区分，正式消费者不得把 V1 简化合同冒充 V1.1 完整合同；
- 未经明确批准，不执行 review、publish 或 current 切换。

## 9. 65E7Q 验收

65E7Q 是第一个数据验收 SKU。V1.1 必须证明：

1. 当前竞品分析智能体旧路径使用的候选全部进入画像可分析范围；
2. 原 Top 3 的购买池、战场、任务、客群、价值锚点、替代压力、参数卖点和量价结果均能从画像回读，完整字段覆盖率为 100%；
3. 每个维度都保存双方事实、计算过程、得分、结论、证据和限制；
4. TCL 65Q9L PRO、华为 VISION 智慧屏 5 PRO 65、创维 65A7H PRO 不得仅因上游复核或“非正式直接竞品”停止后续计算；
5. 新画像可以保留海信 75E7Q、雷鸟 85R69A ULTRA 等新增候选，但必须完整说明其比较角色和是否进入重点名单；
6. 智能体读取 V1.1 后不得发生任何旧原子分析调用；
7. 65E7Q 旧路径全部候选必须逐款对账；旧候选若未进入画像，除非有上述明确 hard exclusion code，否则验收失败；
8. 新旧结论差异必须逐项归因于候选范围或方法差异；任何旧链已知字段在 V1.1 变为 unknown、缺字段或因全局门槛消失均为验收失败；
9. 画像数据验收通过前，不进入 AC、全量草稿或正式发布。

## 10. 全量质量要求

- TV 377、AC 155 权威 SKU 不得漏生成；
- generation failure、跨品类串线、self pair 和重复 pair 为 0；
- 每个合法 pair 均有多维分析状态，不要求每个维度都有强结论；
- 不能再以“有重点结论的 SKU 数量少”证明门槛严格正确；必须统计每个维度的 available/partial/unknown/conflict 和各强度结论数量；
- 全量生成性能不得靠裁剪候选、删除过程数据或降低业务覆盖实现；
- 重证据使用共享 SKU 快照、字典引用和按需证据回读，避免 pair 重复存储。

## 11. 不在本次画像改造范围

- 重新设计飞书卡片；
- 重新设计报告结构；
- 重新设计问答文案；
- 重跑或修改 M03B—M12D；
- 修改旧 M12/M13/M14 历史结果；
- 单卖点因果销量、单卖点 WTP 或价格弹性；
- 自动 publish/current。
